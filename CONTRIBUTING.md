# Contributing to Explorer

Thanks for your interest in contributing! This document describes how to report issues, propose changes, and get a pull request merged.

## Ways to contribute

- **Report bugs** via [GitHub Issues](../../issues) — include macOS version, repro steps, and (when possible) screenshots or screen recordings.
- **Suggest features** via Issues, especially when they map to Windows Explorer behaviors not yet covered.
- **Submit pull requests** for fixes, refactors, or features.

For non-trivial changes, please open an issue first to align on direction before investing time in a PR.

## Development setup

Requirements:

- macOS 14+ (Sonoma or later).
- Xcode 15+ with Swift 5.9+ toolchain.

Clone and open the project:

```bash
git clone https://github.com/<user>/Explorer.git
cd Explorer
open Explorer.xcodeproj
```

Run the `Explorer` target with `⌘+R`. Local builds **do not require code signing** or notarization.

## Branching

- Create feature branches from `main`: `feat/address-bar-edit-mode`, `fix/sidebar-mount-detection`, etc.
- Keep branches focused — one concern per branch.
- Rebase on `main` before opening the PR; avoid merge commits.

## Commit conventions

Follow [Conventional Commits](https://www.conventionalcommits.org/) in **English**, with messages kept to a **single descriptive line**:

```
feat: add editable mode to address bar
fix: prevent crash when listing /private/var
refactor: extract FilesystemService from ContentView
docs: update README with macOS 14 requirement
chore: bump deployment target to macOS 14
```

Rules:

- One commit message line per commit — no body unless strictly necessary.
- Commits should be small and module-scoped (one feature or fix per commit).
- **No** `Co-authored-by` / `Generated by` / similar trailers.
- Stage files explicitly; do not use `git add -A` or `git add .`.

## Code style

- **Swift / SwiftUI** is the primary stack. Avoid deprecated APIs — prefer current SwiftUI idioms.
- **One class per file**, with the exception of `View` types that own a `@State`-only `StatefulWidget`-equivalent helper.
- Avoid free-floating functions inside UI types when they could live in a dedicated component or service.
- Logging: use `os.Logger` (`import OSLog`); never use `print` in committed code.
- Match the conventions and style already present in the codebase.

## Pull request checklist

Before opening a PR, please make sure:

- [ ] The branch is up to date with `main` (rebased, not merged).
- [ ] Tests pass locally (`⌘+U` in Xcode).
- [ ] No new compiler warnings introduced.
- [ ] `CHANGELOG.md` is updated under the `[Unreleased]` section (Added / Changed / Fixed / Removed as appropriate).
- [ ] PR description explains **what** changed and **why** — link any related issue.

PRs should target `main`. Reviewers may request changes; please address feedback in additional commits (don't force-push during review unless asked).

## Reporting security issues

Please **do not** open public issues for security vulnerabilities. Instead, report them privately by emailing the maintainer (see profile on GitHub).
